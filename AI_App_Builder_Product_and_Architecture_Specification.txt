# AI App Builder
## Product Requirements Document, System Architecture, Feature Specification, and Development Roadmap

**Document Type:** Product Requirements Document (PRD) + Software Architecture Specification  
**Project Category:** AI-powered application development platform  
**Primary Platform:** Android  
**Secondary Platforms:** Web and desktop development  
**AI Architecture:** Model-agnostic LLM + Agent Harness + Tool System  
**Build Infrastructure:** GitHub + GitHub Actions  
**Primary Development Languages:** Kotlin, Jetpack Compose, TypeScript, and other languages supported by selected project templates  
**Document Status:** Proposed product specification  
**Version:** 1.0

# 1. Executive Summary

## 1.1 Product Overview

The project is an AI-powered application builder that enables users to create, modify, test, debug, and build real software applications through natural-language conversations.

Users describe an application they want to create, and the platform transforms their requirements into a structured software project. The AI agent plans the implementation, generates source code, creates and modifies project files, runs validation tools, analyzes build errors, applies fixes, and produces downloadable application artifacts.

The platform is designed around an extensible agent harness rather than a single specialized AI model.

The system combines:

- A conversational AI interface.
- A model-agnostic AI integration layer.
- An agent runtime and orchestration engine.
- A persistent project workspace.
- A structured tool-calling system.
- Reusable development skills.
- Project templates and technology-specific knowledge.
- Git and GitHub integration.
- Automated cloud builds through GitHub Actions.
- Automated error analysis and repair.
- Application preview and testing capabilities.
- Project history, checkpoints, and rollback.
- Secure authentication and secret management.
- A modular architecture that supports future expansion.

The initial product will focus on generating native Android applications using Kotlin and Jetpack Compose.

Over time, it should expand into web applications, backend services, cross-platform applications, and full-stack software projects.

## 1.2 Product Vision

**Make software development accessible through conversation while preserving the flexibility, transparency, and control of a real software development environment.**

Users should be able to move from an idea to a working application without manually managing every implementation detail.

Unlike simple code-generation chatbots, the product must operate on real project files, use development tools, execute builds, inspect errors, and iteratively improve its output.

The platform should not merely generate code that appears correct. It should establish a reliable workflow for generating, validating, building, and delivering software.

## 1.3 Product Mission

The mission is to create an accessible, reliable, and extensible AI software development environment that combines the usability of visual AI app builders with the flexibility of coding agents.

The platform should serve both beginners who want to describe an application in plain language and advanced developers who want AI-assisted implementation with direct access to project files, Git history, build logs, and technical configuration.

## 1.4 Core Product Promise

A user should be able to:

1. Describe an application in natural language.
2. Answer clarification questions when necessary.
3. Review the proposed implementation plan.
4. Generate the application project.
5. Inspect and modify the generated source code.
6. Request changes through conversation.
7. Build the application remotely.
8. Receive detailed build progress and error explanations.
9. Allow the agent to repair supported build failures.
10. Download the resulting APK.
11. Continue improving the same project without starting over.

The long-term objective is to make the entire workflow feel like working with a capable software engineering team.

# 2. Competitive Positioning

## 2.1 Competitive Landscape

The product will compete with several categories of tools.

### AI-powered app builders

Examples include Lovable and Base44.

These products emphasize rapid application creation, natural-language instructions, and reduced technical complexity.

### AI coding environments

Examples include Replit and tools built around agentic software development.

These environments emphasize code generation, tool execution, project modification, debugging, and iterative development.

### General-purpose AI development tools

Examples include Google AI Studio and coding agents such as OpenCode and Claude Code.

These tools demonstrate different approaches to AI-assisted coding, model integration, development tools, and agent orchestration.

The proposed product should learn from these categories without attempting to reproduce every feature of every competitor in its initial release.

## 2.2 Primary Differentiation

The product should differentiate itself through the following capabilities.

**1. Mobile-first development experience**

Users can create and manage projects from an Android device instead of requiring a desktop development environment.

**2. Model independence**

The product should support multiple compatible AI providers through a common interface.

**3. Real software project ownership**

Generated projects should be stored in standard repositories with conventional source code and build systems.

**4. GitHub-native development workflow**

Users can connect repositories, inspect changes, review commits, and maintain control over their source code.

**5. Managed cloud builds**

GitHub Actions can provide the initial build infrastructure without requiring the product team to operate a dedicated fleet of Android build servers.

**6. Automated build repair**

Build failures should become structured feedback for the agent rather than dead ends for the user.

**7. Extensible agent harness**

Tools, skills, models, project templates, and validation strategies should be independently replaceable.

**8. Transparent development**

Users should be able to inspect plans, code changes, build logs, validation results, and agent actions.

**9. Reproducible outputs**

The same project should be buildable outside the platform using conventional development tools.

**10. A path toward broader development capabilities**

The architecture should support future web, backend, and cross-platform projects without requiring a complete rewrite of the agent runtime.

## 2.3 Competitive Parity Strategy

The platform should aim for functional parity in key workflows rather than claiming complete parity with every competitor.

# 4. Product Scope

## 4.1 Initial Scope

The first release should focus on a reliable end-to-end Android development workflow.

The MVP should support:

- Creating an Android project from a prompt.
- Generating Kotlin and Jetpack Compose code.
- Editing existing project files.
- Maintaining project context across multiple conversations.
- Connecting to an AI model provider.
- Connecting a project to GitHub.
- Creating or updating a development branch.
- Triggering GitHub Actions builds.
- Tracking build status.
- Retrieving build logs.
- Sending build errors back to the agent.
- Applying corrective changes.
- Rebuilding the project.
- Downloading the resulting debug APK.
- Reviewing changes and reverting to checkpoints.

The initial release should prioritize build reliability, project consistency, and security over a large collection of superficial features.

## 4.2 Explicitly Deferred Features

The following should not be required for the first usable version:

- A proprietary foundation model.
- A custom cloud build farm.
- A fully integrated Android emulator.
- Automatic publication to Google Play.
- Full visual editing comparable to professional design tools.
- Enterprise collaboration features.
- Support for every programming language.
- Unlimited autonomous agent execution.
- Guaranteed generation of production-ready applications from a single prompt.

These features may become valuable later, but they significantly increase cost and complexity.

# 5. Product Principles

The architecture and user experience should follow these principles.

## 5.1 Model-Agnostic Design

The application must not depend on one specific LLM provider.

A common model interface should support multiple providers and, where technically compatible, local or self-hosted models.

## 5.2 Tool-Driven Execution

The agent should interact with the project through explicit tools rather than relying exclusively on generated conversational text.

## 5.3 Persistent Project State

The agent should maintain structured information about the project, its files, dependencies, build configuration, and implementation status.

## 5.4 Incremental Changes

The agent should prefer targeted edits over unnecessarily regenerating the entire project.

## 5.5 Observable Execution

Every meaningful action should produce an inspectable event or result.

## 5.6 Recoverability

Users should be able to recover from failed generations, incorrect edits, and unsuccessful builds.

## 5.7 Secure by Default

AI-generated code must be treated as untrusted input.

The system should use least-privilege permissions, protect secrets, and isolate execution where applicable.

## 5.8 Real Build Validation

The platform must distinguish between code generation, static validation, successful compilation, successful testing, and verified runtime behavior.

A successful build must not be presented as proof that every application feature works correctly.

# 6. System Architecture Overview

## 6.1 High-Level Architecture

The architecture consists of three major environments:

1. Client Application.
2. Agent Runtime and Project Services.
3. External Development Infrastructure.

The system should also distinguish the logical responsibilities of the agent runtime, project workspace, and build service.

### A. Client Application

The client provides the interface through which users manage projects and interact with the agent.

Responsibilities include:

- Chat interface.
- Project dashboard.
- File explorer.
- Diff viewer.
- Build status display.
- Build log viewer.
- Project settings.
- Provider configuration.
- Repository connection.
- Artifact downloads.
- User consent and permission prompts.

The client should remain relatively lightweight.

It should not need to run a full Android SDK, Gradle build environment, or emulator.

### B. Agent Runtime

The agent runtime is the core intelligence and orchestration layer.

Responsibilities include:

- Receiving user instructions.
- Loading project context.
- Selecting the appropriate model.
- Planning changes.
- Selecting tools.
- Executing permitted actions.
- Managing multi-step tasks.
- Validating results.
- Interpreting errors.
- Requesting additional model reasoning.
- Managing retry policies.
- Enforcing budgets and execution limits.
- Maintaining task state.

The agent runtime can initially run inside the client process if the implementation is small and local-only operations are sufficient.

However, a backend-hosted runtime is recommended for production capabilities requiring secure credentials, webhook processing, reliable background execution, or coordination across multiple devices.

### C. Project Workspace

The project workspace stores the actual application being developed.

It contains:

- Source code.
- Resources.
- Project configuration.
- Dependency declarations.
- Build scripts.
- Tests.
- Project-specific instructions.
- Generated documentation.
- Relevant metadata.

The workspace should support local project state and a remote Git repository.

The workspace is not the same thing as the agent's conversation history.

### D. Build Service

The build service executes project validation and compilation.

For the MVP, GitHub Actions can provide the build workers.

Responsibilities include:

- Selecting the correct repository and commit.
- Running the project's build commands.
- Collecting compiler output.
- Running configured tests.
- Producing APK artifacts.
- Publishing build status.
- Preserving relevant logs.
- Reporting structured results to the agent runtime.

### E. AI Model Providers

Model providers perform reasoning and code-generation tasks.

The provider interface should support:

- Text generation.
- Tool calling where available.
- Streaming responses where available.
- Token and usage reporting where available.
- Provider-specific capability declarations.
- Configurable context limits.
- Error normalization.

The platform should not assume that every provider supports identical features.

# 7. Recommended Deployment Architecture

## 7.1 MVP Architecture

The initial system can use the following arrangement:

**Android Client**
- Chat UI.
- Project management.
- Lightweight agent orchestration.
- Local workspace metadata.
- File editing and diff presentation.
- AI provider configuration.
- GitHub integration.
- Build status monitoring.
- Artifact downloads.

**AI Provider**
- Planning.
- Code generation.
- Code editing suggestions.
- Error analysis.
- Repair proposals.

**GitHub Repository**
- Source-code storage.
- Branches and commits.
- Version history.
- Collaboration.
- Workflow configuration.

**GitHub Actions**
- Dependency setup.
- Static checks.
- Gradle compilation.
- Tests.
- APK packaging.
- Artifact upload.

This arrangement minimizes initial infrastructure costs and avoids the need to maintain dedicated build machines.

However, it does not eliminate the need for secure credential management, API access, persistent task state, and reliable asynchronous operations.

## 7.2 Production Architecture

As usage grows, introduce a backend that manages long-running tasks and trusted integrations.

Recommended services:

1. API Gateway.
2. Authentication Service.
3. Project Service.
4. Agent Orchestration Service.
5. Model Gateway.
6. GitHub Integration Service.
7. Build Orchestration Service.
8. Webhook Receiver.
9. Artifact Metadata Service.
10. Usage and Billing Service.
11. Observability Service.

A relational database should store durable metadata, while object storage can be used for files or artifacts where appropriate.

The backend should not automatically become a remote execution environment for arbitrary generated code. Code execution must remain isolated and explicitly controlled.

# 8. The Agent Harness

## 8.1 Definition

The agent harness is the software system that controls how an AI model interacts with a project and its development tools.

The model provides reasoning and generation capabilities.

The harness determines:

- What information the model receives.
- What tasks it may perform.
- Which tools it can use.
- How tool calls are validated.
- How changes are applied.
- How results are checked.
- When execution should continue.
- When to stop and ask the user.
- How failures are handled.
- How usage limits are enforced.

The harness should be treated as an independent, reusable subsystem.

## 8.2 Harness Components

### 8.2.1 Task Manager

Creates and tracks user tasks.

Each task should have:

- A unique identifier.
- Project identifier.
- User request.
- Current status.
- Execution plan.
- Progress information.
- Start and completion timestamps.
- Tool execution history.
- Model usage metadata.
- Result summary.
- Error details where applicable.

Suggested task states:

```text
CREATED
  |
  v
ANALYZING
  |
  v
PLANNING
  |
  v
AWAITING_APPROVAL
  |
  v
EXECUTING
  |
  v
VALIDATING
  |
  v
COMPLETED
```

Additional terminal or intermediate states should include:

```text
FAILED
CANCELLED
WAITING_FOR_BUILD
WAITING_FOR_USER
NEEDS_REVIEW
```

The task state machine should be explicit rather than inferred from chat messages.

### 8.2.2 Planning Engine

Converts natural-language requirements into structured implementation steps.

For example:

```text
User Request:
Create a task management application.

Plan:
1. Inspect the existing project.
2. Identify the application architecture.
3. Define the task data model.
4. Implement the main screen.
5. Add task creation and editing.
6. Persist tasks locally.
7. Add navigation.
8. Run static validation.
9. Trigger an Android build.
10. Analyze and resolve supported failures.
11. Report the final result.
```

The planner should adapt the plan to the current project instead of applying the same template to every request.

### 8.2.3 Context Manager

Collects the relevant information needed by the model.

It should manage:

- User instructions.
- Project specification.
- Project-specific agent instructions.
- File tree.
- Relevant source files.
- Recent changes.
- Dependency information.
- Build configuration.
- Previous task summaries.
- Recent compiler errors.
- Relevant tool results.
- Applicable development skills.

The context manager should avoid sending the entire repository to the model on every turn.

### 8.2.4 Tool Router

Selects and invokes tools through a controlled interface.

The router should validate:

- Tool existence.
- Argument schemas.
- Permission requirements.
- Path restrictions.
- Execution budgets.
- User approval requirements.
- Result size limits.
- Timeouts.

### 8.2.5 Execution Controller

Runs the agent loop.

A simplified loop:

```text
1. Receive task.
2. Load project context.
3. Select model.
4. Ask model to plan or act.
5. Validate the requested action.
6. Execute permitted tools.
7. Record tool results.
8. Update project and task state.
9. Evaluate whether more work is required.
10. Repeat within configured limits.
11. Validate the final result.
12. Return a summary.
```

The model should not be allowed to continue indefinitely.

The controller must enforce maximum iterations, time limits, usage budgets, and cancellation.

### 8.2.6 Validation Engine

Checks whether an action achieved its intended result.

Possible checks include:

- File existence.
- Expected file structure.
- Patch validity.
- Syntax checks.
- Formatting checks.
- Unit tests.
- Dependency resolution.
- Gradle compilation.
- Artifact existence.
- APK metadata checks.
- Instrumentation tests where configured.

### 8.2.7 Repair Controller

Coordinates the recovery workflow when validation fails.

It should:

1. Collect the relevant error information.
2. Classify the failure.
3. Select the appropriate diagnostic tools.
4. Prepare a focused context package.
5. Ask the model for a correction.
6. Validate the proposed changes.
7. Apply the approved changes.
8. Rerun relevant checks.
9. Stop after a configured retry limit.
10. Present unresolved issues clearly.

The repair controller should avoid repeatedly submitting identical errors without new information.

### 8.2.8 Execution Budget Manager

Controls cost and resource consumption.

It should enforce limits for:

- Model calls.
- Token usage.
- Build retries.
- Tool invocations.
- Task duration.
- Concurrent builds.
- Maximum generated files.
- Maximum patch size.
- Total execution cost where estimable.

# 9. Agent Operating Modes

The product should support several operating modes.

## 9.1 Plan Mode

The agent analyzes the request and presents a proposed implementation plan without modifying project files.

Suitable for complex or risky changes.

## 9.2 Agent Mode

The agent executes permitted tasks and validates its work.

Users can observe progress and approve sensitive actions.

## 9.3 Build and Repair Mode

The agent focuses on validating an existing project, interpreting failures, and fixing supported problems.

## 9.4 Explain Mode

The agent explains code, architecture, dependencies, or errors without changing the project unless explicitly requested.

## 9.5 Ask Before Editing Mode

The agent proposes changes and waits for user approval before applying them.

## 9.6 Autonomous Mode

The agent performs multiple steps with limited interaction, subject to configured permissions and execution budgets.

Autonomous mode should be opt-in and should never bypass security restrictions.

# 10. Tool System

## 10.1 Tool Registry

Every tool should have a stable identifier and a machine-readable specification.

Example:

```json
{
  "name": "read_file",
  "description": "Read a text file from the current project workspace.",
  "input_schema": {
    "type": "object",
    "properties": {
      "path": {
        "type": "string"
      }
    },
    "required": ["path"],
    "additionalProperties": false
  }
}
```

The registry should also define:

- Permission requirements.
- Side effects.
- Timeout.
- Output size limits.
- Whether user approval is required.
- Whether the tool is available for a particular project type.
- Whether the operation is reversible.

## 10.2 Core Tools

### Project inspection

- `list_files`
- `read_file`
- `search_files`
- `search_symbols`
- `inspect_project`
- `get_project_metadata`
- `get_dependency_tree`
- `get_git_status`

### File modification

- `create_file`
- `edit_file`
- `apply_patch`
- `delete_file`
- `move_file`
- `rename_file`
- `format_file`

### Project management

- `create_project`
- `select_project_template`
- `update_project_metadata`
- `update_dependency`
- `manage_project_instructions`

### Validation

- `validate_project_structure`
- `run_static_checks`
- `run_unit_tests`
- `validate_gradle_configuration`
- `inspect_build_output`
- `inspect_apk_metadata`

### Git and GitHub

- `create_branch`
- `get_diff`
- `commit_changes`
- `push_branch`
- `create_pull_request`
- `get_workflow_status`
- `get_workflow_logs`
- `download_build_artifact`

### User interaction

- `request_clarification`
- `request_approval`
- `present_diff`
- `report_progress`

Some operations should be implemented as trusted application services rather than tools directly exposed to arbitrary model-generated commands.

## 10.3 Tool Execution Policy

Tools must not receive unrestricted access to the host operating system.

The system should validate paths, arguments, and permissions before execution.

For example, a file-editing tool should only access the authorized project workspace.

A command-execution tool, if added later, should operate within an isolated execution environment with restricted filesystem, network, CPU, memory, and time limits.

# 12. Model Gateway

## 12.1 Objective

The Model Gateway separates the product from individual LLM providers.

It should provide a consistent interface for sending requests, handling responses, invoking tools where supported, and recording usage.

## 12.2 Provider Interface

Conceptually:

```typescript
interface ModelProvider {
  generateResponse(
    request: ModelRequest
  ): Promise<ModelResponse>;

  streamResponse?(
    request: ModelRequest
  ): AsyncIterable<ModelStreamEvent>;

  getCapabilities(): ModelCapabilities;

  estimateUsage?(
    request: ModelRequest
  ): UsageEstimate;
}
```

This is an architectural example, not a complete implementation.

## 12.3 Provider Capabilities

The platform should maintain capability metadata for each configured model.

Possible capabilities include:

- Tool calling.
- Streaming.
- Structured output.
- Large context windows.
- Multimodal input.
- Code-focused generation.
- Image understanding.
- Usage reporting.
- Provider-side caching.

The runtime should not assume that all providers implement these features identically.

## 12.4 Model Routing

Different tasks may benefit from different models.

Example routing policy:

| Task | Preferred Capability |
|---|---|
| Requirement clarification | Strong instruction following |
| Project planning | Strong reasoning |
| Large-scale code generation | Strong coding and context handling |
| Small file edits | Low latency and cost |
| Build-error analysis | Strong debugging |
| UI screenshot analysis | Image understanding |
| Final review | Strong code analysis |

The routing engine should support:

- User-selected default models.
- Task-specific model selection.
- Explicit fallbacks.
- Provider availability checks.
- Configurable cost and latency preferences.
- Capability-based routing.

Automatic routing should remain transparent and configurable.

## 12.5 Provider Failure Handling

The Model Gateway should handle:

- Rate limits.
- Network failures.
- Authentication failures.
- Context-limit errors.
- Invalid tool-call responses.
- Provider outages.
- Unsupported model capabilities.

- View checkpoint.

- Restore checkpoint.
- Revert last task.
- Recover interrupted operation.

## 14.4 Diff Viewer

- Added files.
- Modified files.
- Deleted files.
- Line-level changes.
- Change summaries.
- Files affected by a task.

# 17. GitHub Actions Build System

## 17.1 Objective

GitHub Actions provides a managed execution environment for building and validating projects.

The product can initially avoid operating dedicated Android build servers.

## 17.2 Build Workflow

The normal workflow should be:

```text
Agent modifies project
        |
        v
Changes are committed or pushed
        |
        v
Build workflow is triggered
        |
        v
Workflow checks out an immutable commit
        |
        v
Environment and dependencies are prepared
        |
        v
Static checks and tests run
        |
        v
Gradle assembles the APK
        |
        v
Build results are collected
        |
        +----------------------+
        |                      |
        v                      v
     Success                Failure
        |                      |
        v                      v
 Upload APK             Collect diagnostics
        |                      |
        v                      v
 Notify client           Agent analyzes errors
        |                      |
        v                      v
 Download APK           Apply corrective changes
                               |
                               v
                         Retry if permitted
```

## 17.3 Workflow Responsibilities

The workflow should:

1. Check out a specific source revision.
2. Configure the required JDK.
3. Configure Android SDK components as required.
4. Set up Gradle.
5. Restore safe caches.
6. Run configured validation checks.
7. Run unit tests.
8. Build the requested variant.
9. Preserve useful diagnostic logs.
10. Upload build artifacts when appropriate.
11. Publish a clear success or failure status.

## 17.4 Version Compatibility

The JDK version, Gradle version, Android Gradle Plugin, Kotlin version, and Android SDK configuration must be compatible.

The platform should derive toolchain requirements from the project template or project configuration.

It should not assume that one JDK version works for every project.

## 17.5 Build Job Isolation

Generated code should be treated as untrusted.

Build jobs should use appropriate isolation and least-privilege permissions.

The workflow should not expose deployment secrets, signing credentials, repository administration permissions, or unrelated account credentials to untrusted pull-request code.

For private repositories and sensitive workloads, runner configuration and workflow permissions must be reviewed carefully.

## 17.6 Artifact Handling

Each artifact record should include:

- Artifact identifier.
- Project identifier.
- Repository.
- Commit SHA.
- Workflow run identifier.
- Build variant.
- File name.
- File size.
- Creation time.
- Expiration time.
- Build status.

The application should associate the downloaded APK with the exact build that generated it.

## 17.7 Quotas and Cost

GitHub Actions has usage limits, concurrency limits, and artifact retention policies that depend on account and repository configuration.

The product should not assume unlimited free builds.

It should track build usage, enforce sensible retry limits, and provide clear information about external service requirements.

# 18. Build-Error Analysis and Automated Repair

## 18.1 Objective

Build failures should become structured input for the agent's diagnostic workflow.

The platform should not merely return an unfiltered wall of terminal output.

## 18.2 Error Processing Pipeline

When a build fails:

1. Retrieve the workflow conclusion.
2. Retrieve relevant logs.
3. Identify the failing step.
4. Extract compiler and Gradle diagnostics.
5. Classify the error.
6. Identify likely relevant source files.
7. Retrieve those files and their current contents.
8. Prepare a focused diagnostic context.
9. Ask the model to propose a fix.
10. Validate the proposed change.
11. Apply the change if authorized.
12. Commit or push according to policy.
13. Trigger a new build.
14. Evaluate the result.
15. Stop after the retry budget is exhausted.

## 18.3 Error Categories

Initial categories should include:

- Kotlin compilation failure.
- Gradle configuration failure.
- Dependency resolution failure.
- Android resource compilation failure.
- Manifest configuration failure.
- Missing resource.
- Incorrect import.
- Type mismatch.
- Unresolved reference.
- SDK or toolchain mismatch.
- Unit-test failure.
- Packaging failure.
- Artifact upload failure.
- Workflow permission failure.
- Network or external-service failure.

## 18.4 Diagnostic Context

The agent should receive a concise, structured package rather than unnecessarily large logs.

Example:

```json
{
  "build_status": "failure",
  "failed_step": "assembleDebug",
  "error_category": "kotlin_compilation",
  "source_file": "app/src/main/java/example/HomeScreen.kt",
  "diagnostics": [
    {
      "message": "Unresolved reference",
      "line": 42,
      "column": 17
    }
  ],
  "commit_sha": "example-commit-sha"
}
```

This is an illustrative schema, not a literal expected build response.

The runtime should verify that the error corresponds to the current project revision before applying a fix.

## 18.5 Retry Policy

A reasonable starting policy is to allow a small number of automatic repair attempts per build task.

For example:

- One initial build.
- Up to three repair attempts.
- A final verification build when appropriate.

The limit should be configurable.

The agent must stop when:

- The error is outside supported categories.
- The same failure repeats without meaningful changes.
- The budget is exhausted.
- A required secret or permission is missing.
- The next action is destructive or unsafe.
- User intervention is necessary.

## 18.6 Repair Quality

A successful compilation is necessary but insufficient.

The system should also evaluate:

- Whether the original request was implemented.
- Whether unrelated files were modified.
- Whether existing behavior was preserved.
- Whether tests pass.
- Whether the fix introduces obvious security problems.
- Whether the final output matches the intended project configuration.

The final response should distinguish verified outcomes from unverified assumptions.

# 21. Security Architecture

Security must be treated as a foundational requirement.

## 21.1 Trust Boundaries

The system should distinguish between:

- User input.
- Model output.
- Generated source code.
- Repository contents.
- External dependencies.
- Build workflows.
- Application credentials.
- Platform credentials.
- Build artifacts.

Neither model output nor repository content should be assumed to be trustworthy.

## 21.2 API Key Handling

The product must never hardcode private model-provider API keys into generated application source code.

Preferred options include:

1. A backend-hosted model gateway that keeps provider credentials server-side.
2. User-supplied provider credentials stored securely on the device, if direct client-to-provider access is intentionally supported.
3. Short-lived credentials where the provider supports them.

If credentials are stored locally, use platform-appropriate secure storage.

The application must never send its own backend administrative credentials or GitHub integration secrets to the model.

## 21.3 GitHub Credential Security

Use the smallest practical permission scope.

Credentials should:

- Be encrypted at rest when stored by a backend.
- Never be written to logs.
- Never be included in model prompts.
- Never be embedded in generated APKs.
- Be revocable.
- Be rotated or expire where supported.
- Be isolated by user and project.

## 21.4 Generated Code Security

Generated code must be reviewed and tested according to the risk level of the project.

The system should detect or flag:

- Hardcoded credentials.
- Dangerous permission requests.
- Insecure network configurations.
- Obvious sensitive-data exposure.
- Unnecessary privileged dependencies.
- Suspicious build-script behavior.
- Unsafe deserialization patterns where detectable.
- Insecure storage practices.

Automated scanning cannot guarantee that code is secure.

## 21.5 Workflow Security

Build workflows should:

- Use minimal token permissions.
- Avoid exposing secrets to untrusted code.
- Pin third-party actions to reviewed commit SHAs in production.
- Use trusted workflow definitions.
- Validate webhook signatures.
- Validate repository and workflow identifiers.
- Restrict artifact access.
- Apply appropriate execution limits.
- Avoid executing arbitrary privileged commands supplied directly by the model.

The platform should carefully distinguish trusted project-owner actions from untrusted pull-request or generated-code execution.

## 21.6 Build Artifact Security

The system should validate the association between an artifact, workflow run, repository, and source revision.

Artifacts should not be treated as trusted merely because they were uploaded by a workflow.

## 21.7 User Approval

Require explicit confirmation for high-impact operations such as:

- Deleting substantial project content.
- Overwriting important user files.
- Changing repository visibility.
- Publishing a release.
- Modifying production deployment configuration.
- Using signing credentials.
- Triggering externally billable services beyond configured limits.

## 21.8 Threat Modeling

Before production release, conduct a threat-modeling exercise covering:

- Prompt injection.
- Malicious repository instructions.
- Dependency supply-chain attacks.
- Credential leakage.
- Unauthorized repository access.
- Workflow permission escalation.
- Malicious build scripts.
- Artifact substitution.
- Cross-user data exposure.
- Denial of service through repeated model or build requests.

Specific availability and latency targets should be set after measuring real workloads.

- GitHub API rate limits.
- Expired authorization.
- Duplicate webhook delivery.
- Partial file operations.
- Client disconnection.
- Failed artifact downloads.
- Interrupted agent tasks.

# 33. Critical Engineering Decisions

The following decisions should be made explicitly before implementation.

## Decision 1: Local Harness or Backend Harness?

**Recommendation:** Begin with a lightweight client-side harness if the initial implementation can operate securely without privileged backend access. Introduce a backend for durable orchestration and trusted integrations as production requirements emerge.

A client-only architecture reduces initial infrastructure but makes secure credential management, reliable background execution, and centralized task coordination more difficult.

## Decision 2: Direct Model Calls or Model Gateway?

**Recommendation:** Define a provider abstraction immediately. Use a backend model gateway when shared service credentials, centralized billing, provider routing, or durable execution are required.

Avoid hardwiring the application to a single provider's API.

## Decision 3: Local Android SDK or GitHub Actions?

**Recommendation:** Use GitHub Actions for the initial cloud build workflow.

Do not require a complete Android build toolchain on the user's phone.

Local compilation can be explored later for environments where it is practical.

## Decision 4: Generate From Scratch or Use Templates?

**Recommendation:** Use tested templates as the default.

The agent should adapt a known-good project instead of inventing every build configuration from scratch.

## Decision 5: Automatic Push or Approval Before Push?

**Recommendation:** Make the policy configurable.

For a beginner-friendly workflow, automatically push to a dedicated agent branch may be appropriate after initial authorization.

For established repositories, use explicit approval or pull requests.

## Decision 6: Unlimited Repair or Bounded Repair?

**Recommendation:** Use bounded repair loops with a configurable retry budget.

Repeated builds without meaningful progress should stop and request intervention.

## Decision 7: Store Source Code Locally or Remotely?

**Recommendation:** Support local workspace state and GitHub-backed persistence.

A production backend may store metadata and snapshots, but GitHub should remain a conventional source-control option rather than a proprietary lock-in mechanism.

## Decision 8: Build Infrastructure Ownership

**Recommendation:** Start with GitHub Actions.

Introduce dedicated build infrastructure only when cost, latency, concurrency, availability, or product-control requirements justify it.

# 34. Main Risks and Mitigations

## Risk: Incorrect Code Generation

Mitigation:

- Use stable templates.
- Apply incremental patches.
- Run static checks.
- Build early.
- Maintain regression tests.
- Track repair success rates.

## Risk: Expensive Repair Loops

Mitigation:

- Set retry limits.
- Classify errors.
- Avoid repeated identical requests.
- Track model usage.
- Cache suitable intermediate results.

## Risk: GitHub Rate Limits

Mitigation:

- Use webhooks where appropriate.
- Cache metadata.
- Apply exponential backoff.
- Handle rate-limit responses.
- Avoid unnecessary polling.

## Risk: Credential Exposure

Mitigation:

- Use scoped credentials.
- Keep secrets outside source code.
- Redact logs.
- Isolate user authorization.
- Avoid exposing secrets to generated workflows.

## Risk: Generated Code Executes Unsafe Commands

Mitigation:

- Treat generated code as untrusted.
- Use isolated runners.
- Restrict permissions.
- Validate workflow changes.
- Avoid unnecessary secrets.
- Review dangerous build-script modifications.

## Risk: Poor Visual Quality

Mitigation:

- Use design specifications.
- Maintain reusable components.
- Add visual regression tests.
- Introduce screenshot-based iteration when infrastructure is available.

## Risk: Inconsistent Project State

Mitigation:

- Use immutable build revisions.
- Maintain checkpoints.
- Track Git status.
- Validate workspace synchronization.
- Recover interrupted tasks explicitly.

## Risk: Vendor Lock-In

Mitigation:

- Use standard source code.
- Keep model integrations modular.
- Use conventional Git repositories.
- Preserve standard Gradle buildability.
- Separate orchestration logic from provider-specific APIs.

# 37. Definition of Success

The product should be evaluated primarily on whether users can successfully create and improve real applications.

Important measures include:

### First-Build Success Rate

The percentage of generated projects that compile successfully on the first build.

### Final Build Success Rate

The percentage of project-generation tasks that eventually produce a successful build within the configured retry budget.

### Repair Success Rate

The percentage of supported build failures resolved by the agent.

### Time to Working Application

The elapsed time between the user's initial request and the first verified successful build.

### Requirement Fulfillment

The degree to which the resulting application implements the user's requested functionality.

### Regression Rate

The percentage of changes that unintentionally break previously working functionality.

### Cost per Successful Build

The total model, infrastructure, and build-service cost associated with successfully producing a build.

### User Retention

The percentage of users who return to improve existing projects or create additional applications.

### Project Portability

The percentage of generated projects that can be built outside the platform using their documented standard toolchain.

These metrics should be measured over real usage rather than inferred from model confidence.

# 38. Final Product Strategy

The project should not attempt to become a complete competitor to every AI coding platform in its first release.

Its strongest initial strategy is to deliver one complete, reliable, differentiated workflow:

**Natural-language idea → AI planning → real Android project → controlled file editing → GitHub synchronization → cloud build → automated repair → downloadable APK.**

This workflow should be reliable before adding more project types or advanced visual features.

The agent harness should remain the central architectural asset.

The model is replaceable. Build infrastructure is replaceable. Templates are replaceable. Individual tools are replaceable.

The orchestration system, project-state management, validation pipeline, security model, and feedback loop are the components that turn a general-purpose LLM into a dependable application-building product.

The product should therefore invest early in:

1. Reliable agent execution.
2. Correct project context.
3. Safe file operations.
4. Tested templates.
5. Immutable build revisions.
6. Structured error analysis.
7. Bounded automated repair.
8. GitHub integration.
9. Secure credential handling.
10. Measurable end-to-end quality.

The long-term vision is a model-independent AI development platform that can transform natural-language requirements into maintainable, testable, portable software projects while giving users meaningful control over their code, repositories, and generated artifacts.

# 39. Immediate Implementation Recommendations

The project should be developed in the following order:

1. **Choose the execution architecture:** Decide which responsibilities belong on the Android client and which require a backend.
2. **Build a minimal Android client:** Implement the project list, chat interface, file viewer, and task status UI.
3. **Create a model-provider abstraction:** Avoid coupling the agent to one provider's API.
4. **Implement the smallest useful harness:** Add planning, file tools, tool validation, and bounded execution.
5. **Start from a tested Android template:** Generate projects by adapting a known-good Kotlin and Jetpack Compose project.
6. **Integrate GitHub securely:** Use narrowly scoped authorization and a dedicated development branch.
7. **Create the Actions workflow:** Build a specific commit, run tests, and upload the debug APK.
8. **Implement build monitoring:** Track workflow state, logs, and artifact metadata.
9. **Add automated repair:** Feed structured build diagnostics back into the agent and enforce retry limits.
10. **Evaluate end-to-end quality:** Measure build success, repair success, cost, and requirement fulfillment before expanding scope.

## Recommended MVP Definition

The first release should be considered successful when a user can describe a simple Android application, review the plan, generate and modify a real Kotlin/Compose project, push it to GitHub, build it through GitHub Actions, receive a useful explanation if the build fails, and download a verified APK when it succeeds.

That end-to-end workflow is the foundation on which more advanced features should be built.
